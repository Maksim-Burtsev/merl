### Fixed

- `d` on a method called on a local, a parameter or a field named exactly like a project class (Java `Pot Kettle; Kettle.boil()`, Kotlin `val Kettle = Pot(); Kettle.boil()`) lands on the method of the variable's type (`Pot.boil`) instead of the class's namesake or a picker, and in Rust a `let` or a parameter named like a struct with named fields (`let Kettle = Pot::make(); Kettle.boil()`) is the variable it is, so `d` on it lands on the `let` and its methods on `Pot`'s (#1515)
- In Java, `d` on a method called on a field inherited from a base class in another file, named like a project class (`Gravy.drizzle()` in a subclass of a class declaring `Boat Gravy`), lands on the method of the field's type (`Boat.drizzle`) instead of the class's namesake (#1515)
- In Java, `d` on a method called on a field inherited from a base class and named like a project class lands on the method of the field's type also in a file that checks the name with `instanceof` (`if (Tagine instanceof Cassole) { Tagine.simmer(); }` lands on `Cassole.simmer`, not the class `Tagine`'s) (#1515)
- In Java, `d` on a method called on the parameter of a lambda assigned to a local whose type is written (`Consumer<Pot> f = Kettle -> Kettle.boil();`, also `Function`, `Predicate`, `UnaryOperator`) lands on the method of that type instead of a picker (#1515)
