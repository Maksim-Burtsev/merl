### Fixed

- `d` in Scala no longer jumps to the outer type's member on a name bound again by a `for` generator or enumerator, a pattern `val`, `given`, `implicit val` or a colon lambda, or after a closed `case` arm on the same line: it opens the picker (#1389)
- `d` on `this.member` inside a one-line anonymous class (`new Kettle { … this.pour() }`, `object : Kettle() { … }`) in Java, Kotlin and Scala no longer jumps to the outer class's member of that name: it opens the picker (#1389)
- `d` in Scala on a name bound by a `for (x <- …)` generator on the cursor's line lands on the generator instead of the outer type's member, and `x.member` after a lambda, `case` arm or `for` that closed earlier on the line goes to the outer `x`'s type instead of a picker (#1389)
- `d` on `this.member` inside a Scala anonymous class written over several lines (`new Kettle {`, `new Kettle with Mixin {`) opens the picker instead of jumping to the outer class's member (#1389)
- `d` in Scala on a name bound by a later generator of a `for` (`for (m <- ms; x <- List(m)) println(x)`) lands on that generator instead of the outer type's member (#1389)
- `d` in Scala on a name bound by a `for { … }` or a bracketless `for … do` / `yield` generator, on the cursor's line or the lines above (`for { m <- ms; x <- List(m) } println(x)`), lands on that generator instead of the outer type's member (#1389)
- `d` on a bare call inside a one-line anonymous class (`new Kettle { def z() = pour() }` in Scala, `new Kettle() { void z() { pour(); } }` in Java) lands on the base's member instead of the outer class's (#1389)
- `d` in Scala on a name bound by a tuple pattern in a `for` generator (`for { (n, x) <- pairs } println(x)`), or by a generator of a `for { … }` / `for ( … )` over several lines whose body opens on `} {` or `) {`, lands on that generator instead of the outer type's member (#1389)
