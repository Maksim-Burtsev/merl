### Fixed

- `d` on a type parameter named like a type of the project (`class Box<Cup>` while `class Cup` exists) in C#, Rust, Go and C++ lands on the parameter inside its generic instead of on the project type (#1438)
- `d` on a member of a value whose type is a type parameter with no bound (`x.pour()` in `func f[T any](x T)`, `template <typename T> void f(T x)`, `func f<T>(_ x: T)`, `fn f<T>(x: T)`) in Go, C++, Swift and Rust no longer jumps to a project type's method of that name; in Go, a bound interface of the project (`[T Pourer]`) leads to its method (#1438)
- `d` on a member of a field typed by such a parameter (`held.pour()`, `this->held.pour()`, `self.held.pour()` inside `Rack<T>`) in C++ and Swift, and on `x->pour()` with a parameter `T* x` in C++, no longer jumps to a project type's method of that name (#1438)
